Abstract 

Operations research (OR) problems are often described by stakeholders with incomplete knowledge and vague expressions in real-world settings. Such ambiguous descriptions can not be used to formulation directly. Thus, automating OR problems solving requires processing this logical inconsistency in advance. To address this challenge, we propose an Ambiguity-Aware Multi-Agent Framework for Automated OR Problem Solving, AMAO , which first addresses logical inconsistency through two-stage alignment before downstream formulation and coding. Specifically, a logical alignment agent with OR-guided experts structure first produces an aligned candidate using supervised routing over variables, parameters, objectives, and constraints. Then, a source-sufficiency verifier determines whether the original description supports the required repairs. When evidence is insufficient, an interactive repair agent requests additional information and revises the description before modeling and coding. In addition, an ambiguity-aware benchmark and its matched dialogue extension are proposed to support evaluation of both stages. The 32B model achieved 86.8% error-recovery success and 60.4% solution accuracy, reaching 1.98 and 1.86 times the respective base-model scores. The 8B model achieved 47.9% solution accuracy, exceeding the best evaluated variant such as DeepSeek-V4-Flash and Claude-sonnet-4.5. Interactive repair further achieved 90.71% complete-description accuracy when cases requiring clarification. These results support combining context-based repair with evidence assessment and targeted user clarification for automated OR modeling. 

Keywords: Artificial intelligence, automated operations research, multi-agent systems, logical inconsistency, mixture of experts

1. Introduction 

Operations research (OR) supports decisions in many fields, such as supply chain manage-ment (Lambert & Cooper, 2000), healthcare operations (Bertsimas et al., 2008), and logistics planning (Daganzo, 1987). However, applying OR remains challenging for users without specialist modeling expertise. Compared with a widespread adopted method, machine learning (ML), which is supported by mature and integrated tool-chains spanning the full application workflow, OR lacks end-to-end support from problem elicitation and specification to math-ematical formulation and implementation. Recent large language model (LLM) approaches to OR (LLM4OR) mainly focus on translating well-structured, self-contained descriptions into mathematical models (Ramamonjison et al., 2023; AhmadiTeshnizi et al., 2023; Huang et al., 2025b). However, this translation only addresses a downstream task within the broader problem-solving workflow. In practice, stakeholder-provided descriptions may instead be vague, incomplete, or internally inconsistent, producing discrepancies that we term logical inconsistency . For example, an uncertain business goal may be stated as a mandatory constraint, or imperfect recall may introduce an incorrect capacity bound. Such inconsistencies can arise from human errors, biased stakeholder perspectives, incomplete expertise, and imperfect recall. Furthermore, this upstream complexity makes it challenging for LLM agents to extract, structure, and translate problem descriptions into well-defined mathematical models, as ambiguity is not merely a linguistic issue but a modeling-relevant signal that may change the underlying OR problem (Monks, 2016). Automated modeling therefore requires upstream logical alignment to establish a clear and consistent problem description that accurately reflects the stakeholder’s intended optimization problem. One feasible approach is to reconcile accounts from multiple stakeholders, drawing on approaches such as brainstorming and the Delphi method (Sutton & Hargadon, 1996; Dalkey & Helmer, 1963). Specifically, we conduct a exploratory experiment, as shown in Figure 1.1, to examines alignment when several descriptions provide redundant information about the same problem. The results show that the performance decreases as fewer descriptions are available, illustrating the value of corroborating evidence. Because collecting multiple accounts can be costly, an important challenge is to recover reliable modeling information from a single, sparse description under logical inconsistency. Researches have shown that linguistic expressions can reflect uncertainty, limited knowledge, and personal characteristics (Lakoff, 1973; Mairesse et al., 2007). Such semantic cues can help identify potentially erroneous OR elements when interpreted alongside the surrounding context and relationships among model components. When the available context is insufficient to support reliable alignment, a second stage of user interaction is needed to obtain additional information and refine the problem description. To fill this gap, we propose an Ambiguity-Aware Multi-Agent Framework for Automated 

OR Problem Solving, AMAO . First-stage logical alignment uses semantic cues and contextual evidence to produce a candidate description. A source-sufficiency verifier then determines whether the original information supports all required repairs. Cases requiring additional evidence proceed to interactive repair, which asks targeted questions and updates the description from user feedback. Mathematical modeling and coding follow alignment, while unresolved cases are escalated for human resolution. The main work and contributions are summarized as follows: • Benchmark. We construct two complementary benchmarks for logical alignment under logical inconsistency, comprising an ambiguity-aware alignment benchmark and a matched multi-turn dialogue benchmark. The former benchmark connects stakeholder personas, vague semantic cues, and controlled logical errors through a three-layer taxonomy. Error-level recoverability annotations further distinguish corrections supported by the initial description from those requiring additional information. Building on the same problem 3instances, the dialogue benchmark introduces external information sources and diverse user-feedback conditions, including incomplete and unreliable responses. • Methodology. We propose AMAO, a two-stage multi-agent framework that integrates logical alignment into the process of translating stakeholder descriptions into optimization models and executable code. In the first stage, the logical alignemnt agent uses a mixture of experts (MoE) with low-rank adaptation (LoRA) and supervised sentence-level routing over four OR components. Then, a verifier agent, refined through trajectory-guided harness optimization, assesses whether the available information supports direct repair. When additional evidence is required, the interactive agent in the second stage conducts targeted user interaction and progressively revises the description from feedback. • Assessment. Experiments demonstrate substantial gains in logical alignment and downstream solution accuracy. Compared with its base counterpart, the 32B AMAO-tuned model increases overall success rate (SR) from 43.8% to 86.8% and solution accuracy (AC) from 32.5% to 60.4%, reaching 1.98 and 1.86 times the respective base-model scores. Notably, with only an 8B backbone, AMAO achieves 47.9% solution accuracy, surpassing the best evaluated variants, DeepSeek-V4-Flash and Claude-sonnet-4.5. Interactive repair further achieves 90.71% complete-description accuracy on repairable dialogue tasks when cases requiring clarification. These findings effectively support combining specialized OR alignment with targeted user interaction to handle ambiguous and incomplete problem descriptions. 

1.1. Related Literature 1.1.1. LLMs for OR 

LLMs support natural language processing (NLP) tasks including summarization, question answering, translation, and code generation (Chowdhery et al., 2023; Touvron et al., 2023). Chain-of-thought (CoT) prompting elicits intermediate reasoning steps (Wei et al., 2022). Related approaches explore progressive hints (Zheng et al., 2024), feedback-based reflection (Shinn et al., 2023), and structured reasoning search (Yao et al., 2023). In OR, LLM-based modeling seeks to reduce the expertise and effort needed to translate business descriptions into mathematical optimization problems. NL4Opt studies the translation of natural-language descriptions into mathematical formulations (Ramamonjison et al., 2022). Subsequent work includes multi-agent frameworks such as CoE (Xiao et al., 2024) and OptiTrust (Lima et al., 2025). Public resources and model-adaptation studies include NLP4LP (AhmadiTeshnizi et al., 2024), MAMO (Huang et al., 2025b), ORLM (Huang et al., 2025a), LLMOPT (Jiang et al., 42025a), and StepORLM (Zhou et al., 2026). DPLM (Zhou et al., 2025), DRoC (Jiang et al., 2025b), and LLM4OuU (She et al., 2026) extend the scope to additional problem types and settings. 

1.1.2. Logical Inconsistency 

Logical consistency is a concern in secure and trustworthy AI (Bonagiri, 2025). LLMs may generate plausible but factually incorrect statements or fail to maintain consistent knowledge representations (Ghosh et al., 2025). Their predictions can also differ after meaning-preserving changes to the input (Ravichander et al., 2020; Elazar et al., 2021). Approaches to these problems include data augmentation (Asai & Hajishirzi, 2020; Ray et al., 2019), reinforcement learning from human feedback (Ouyang et al., 2022), prompt optimization (Marvin et al., 2024), and direct preference optimization (DPO) (Rafailov et al., 2023). In OR, much existing work assumes descriptions with explicitly specified objectives, con-straints, and decision variables. Stakeholders may instead provide incomplete or conflicting information during initial problem elicitation. This creates an upstream challenge for LLM4OR, where the intended problem must be established before its formulation can be assessed. AMAO addresses this challenge by distinguishing repairs supported by the initial description from those requiring further information.

2. Problem Setup 

In practical OR problem elicitation, users may express uncertainty through approximation, hesitation, exaggeration, or other vague semantic cues. These cues may signal errors in the stated decision variables, parameters, objectives, or constraints. Logical alignment uses cue– error associations, cross-sentence context, and necessary OR relationships to identify erroneous elements and support their correction. 5Let d denote an ambiguous natural-language description. Within this pipeline, alignment comprises two stages determined by the evidence available for repair. First, the logical alignment agent uses vague semantic cues to locate potentially erroneous elements. It then combines contextual information with necessary OR relationships to produce an initial repaired candidate ˜d(0) .However, the initial description may lack sufficient evidence to support a unique repair. For example, the actual budget may be 100 while the user reports approximately 80. Both values may yield feasible models, yet the context may provide no basis for identifying 100 as the intended value. The error is then unrecoverable from the initial description alone. An error is recoverable when the available semantic and contextual information uniquely supports its correction. Recoverable errors permit direct repair, whereas unrecoverable errors require additional user information. In the latter case, alignment proceeds to the second stage, where the agent asks questions and iteratively repairs the description using feedback. Users may consult experts, information systems, or operational records to obtain the missing evidence. 

3. Ambiguity-Aware OR Benchmarks 

We construct an ambiguity-aware alignment benchmark and extend its instances into a matched multi-turn dialogue benchmark. The alignment benchmark pairs ambiguous descrip-tions with clean references for evaluating error localization and repair. Its dialogue extension adds external information and user feedback to support verification and interactive repair evaluations on the same OR problems. 

3.1. Ambiguity-Aware Alignment Benchmark 

The ambiguity-aware benchmark evaluates recovery of an OR problem from an imperfect stakeholder description. Each instance pairs an ambiguous description with a clean reference and annotations of injected OR errors. We generate three descriptions per source problem from NL4Opt (Ramamonjison et al., 2023), NLP4LP (AhmadiTeshnizi et al., 2024), and MAMO-Complex (Huang et al., 2025b). The resulting benchmark contains 2049 descriptions, of which 414 form the test set. 6Figure 3.1: An ambiguity-aware benchmark example. The clean reference and generated stakeholder description appear above the three cue–error correspondences. 

Persona-Guided Construction. A conductor LLM implemented coordinates generation through a three-layer taxonomy of stakeholder personas, vague semantic cues, and OR-level errors. For example, uncertain recall may produce approximate wording around an incorrect capacity value. The taxonomy contains nine personas, eight semantic-cue types, and eight error types. The conductor selects compatible combinations and generates descriptions using the tool library in Appendix B. Figure 3.1 illustrates how semantic cues correspond to injected errors within an example description. 

Quality and Coverage. Candidates undergo LLM-based verification, deterministic filter-ing, and two-round human sampling checks, with the procedures given in Appendix B.4. Dataset coverage and quality assessment are detailed in Appendix B.4. An auxiliary human-likeness assessment provides further support for the descriptions’ linguistic naturalness (Appendix B.8). 

3.2. Multi-Turn Dialogue Benchmark 

Some errors in the ambiguity-aware benchmark require information beyond the initial description. Their evaluation therefore requires a setting in which agents can request additional evidence. We extend the same problems into interactive tasks that assess clarification decisions, information acquisition, and incorporation of feedback into repaired descriptions. 

Benchmark Contents. Each task includes an ambiguous description, an initial aligned draft, stakeholder records, a response policy, and evaluation references. Records may contain current, incomplete, outdated, or conflicting information about the problem. For example, 7a disputed capacity may appear in both current and outdated records; the response policy determines which information the user provides. Evaluation references specify clarification requirements, corrective facts, the clean description, and the appropriate final outcome. Each source-insufficient description is paired with six feedback conditions, covering complete, partial, uncertain, incorrectly retrieved, conflicting, and unavailable information. Construction combines missing-information annotation, reference-based auditing, and consistency checks, as detailed with the partitions and task specifications in Appendix B.7. 

4. Ambiguity-Aware Multi-Agent Framework for Automated OR 

In this section, we present AMAO as a two-stage alignment framework followed by modeling and coding, as shown in Figure 4.1. The logical alignment agent produces a candidate description, and the verifier assesses whether the original information supports the required repairs. Descriptions classified as source-sufficient proceed to mathematical modeling and code generation. For other descriptions, the interactive repair agent requests additional information and updates the candidate from user feedback. Users may consult operational records or other sources during this process. Interaction ends when the required facts are incorporated or unresolved issues are escalated for human resolution.

Following initial alignment, the verifier assesses whether the original description d supports all required repairs. It considers candidate repairs, supporting and conflicting evidence, and unresolved alternatives for each modeling-relevant issue. Admissible evidence includes explicit statements, cross-sentence context, and necessary OR relationships. An issue is recoverable when this evidence uniquely determines its correction. The verifier generates an action and a report according to 

(v, w ) ∼ πver (· | d, p ver ) , v ∈ { Accept , Clarify }, (8) where πver is the source-sufficiency verifier and pver is its prompting harness. The report 

w contains decisive evidence, unresolved information requirements, and the rationale for action v. The verifier returns Accept when every modeling-relevant issue is recoverable and 

Clarify otherwise. For clarification, w identifies information requirements without prescribing unsupported replacement values. 

Audit-Trajectory-Based Harness Optimization. We refine the audit instructions and evidence-boundary rules in pver using development trajectories while keeping the underlying LLM fixed. Each trajectory records the decision, decisive evidence, unresolved issues, and explanation. Agent-assisted error analysis compares these records with source-sufficiency annotations to derive rules for interpreting ambiguous or conflicting evidence. We consolidate the rules under the uniqueness criterion and re-evaluate the revised harness on development data. The resulting harness is assessed on a source-disjoint holdout and frozen before testing. Appendix C.2 specifies the ledger, rules, and implementation settings, while Appendix D.1 reports refinement and holdout results.

We evaluate the logical alignment agent on the ambiguity-aware benchmark, then use its dialogue extension to assess source-sufficiency verification and interactive repair. Finally, we examine their combined contribution through recorded downstream outcomes. 

5.1. Experimental Setup 

Data. We split source problems into 80% training and 20% test partitions before generating ambiguous descriptions. The test set contains 138 NL4Opt-view, 147 NLP4LP-view, and 129 MAMO-C-view descriptions, where -view denotes the ambiguous benchmark. Its dialogue extension contains 2029 tasks linked to these same 414 descriptions. Agent development and holdout problems are disjoint from the test set. 

Implementation. Fine-tuning uses eight NVIDIA A100 GPUs, each with 80GB memory. Temperatures are 0.3 for description generation and 0 for first-stage evaluation. The verifier and interactive repair agent use GPT-5.5 with high reasoning effort, fixed model parameters, and development-refined prompts frozen before testing. Interactive tasks use saved Qwen3-8B drafts, a deterministic user simulator, and at most five feedback turns. Gold routing and supplied issue slots define a controlled repair evaluation with a known issue inventory. These slots are distinct from the verifier-generated report w. Predicted routing is assessed separately in Section 5.4.3. Appendix C provides full settings. 

Metrics and Runs. Error-level localization recall (LR) measures identification of erroneous elements, while success rate (SR) additionally requires correct repair. Solution accuracy (AC) is measured per description. Verifier metrics assess source-sufficiency classification, while interactive metrics assess fact recovery, complete-description repair, and termination (Appendix A). First-stage main results report means and standard deviations over three runs. Verifier and full interactive-test results each use one frozen-protocol run; interactive repeatability uses five runs on a fixed subset.

6. Discussion 

The two alignment stages separate repairs supported by the original description from those requiring new information. Source-sufficiency verification connects these stages, while escalation retains human oversight when essential facts remain unavailable. The repair ablations further show that obtaining correct facts and preserving a complete OR specification are distinct requirements. Linking each edit to supporting feedback helps address both during interaction. The evidence is conditional on the evaluation setting. Interactive tasks supply an issue inventory and controlled user responses, so their scores do not establish performance with unrestricted human feedback. Verifier errors can bypass needed clarification, and repeated 21 runs show variation in repair reliability. Finally, the predicted-route outcome is reconstructed from recorded branches, with unchanged outcomes assumed for false clarifications. Prospective evaluation of the complete cascade with real users is needed to measure these effects jointly. 

7. Conclusion 

We present AMAO for two-stage logical alignment of ambiguous OR descriptions. OR-guided experts first repair errors using the available context, and a source-sufficiency verifier identifies cases requiring additional information. An interactive agent then acquires missing evidence and revises the description before mathematical modeling and coding, escalating unresolved cases for human resolution. The ambiguity-aware benchmark and its dialogue extension jointly support evaluation of these components. First-stage alignment achieved 86.8% SR and 60.4% solution AC with a 32B backbone. The 8B model exceeded the best evaluated API-based variant in overall AC. Interactive repair achieved 90.71% description-level Repair AC under gold routing and supplied issue slots. Recorded-branch analysis also indicates downstream gains from clarification. These findings support incorporating evidence assessment and information acquisition into automated OR modeling, with full-cascade evaluation remaining an important next step.

Appendix B.1. Original Benchmarks 

We use the LLM4OR benchmarks NL4Opt (Ramamonjison et al., 2023), NLP4LP (Ahma-diTeshnizi et al., 2024), and MAMO-Complex (Huang et al., 2025b). 

NL4Opt contains 1101 annotated linear programming problems across six domains, origi-nating from the NL4Opt competition. Each problem includes a natural-language description and an intermediate representation of parameters, variables, linear constraints, and the objective. Its original split contains 713 training, 99 validation, and 289 test problems. 

NLP4LP draws from optimization textbooks and lecture notes covering facility location, network flow, scheduling, and portfolio management. Each instance includes a description, a sample parameter file, and an optimal value obtained from a textbook solution or manual solving. 

MAMO-Complex contains 211 undergraduate-level problems involving linear program-ming (LP) and mixed-integer linear programming (MILP). These problems cover diverse applications and theoretical challenges in mathematical optimization.

Definition. Recoverability describes whether information available before clarification uniquely determines an injected error’s correct repair. Assessment assumes that the affected element has been localized and does not measure detection difficulty. An error is recoverable 

when the available evidence uniquely determines its replacement. It is unrecoverable when materially different repairs remain compatible with that evidence or an essential fact is absent. 

Evidence Boundary. Admissible evidence comprises the ambiguous description, cross-sentence context, and necessary OR structural or objective real-world relationships. Error-location metadata specifies which element is assessed under this evidence boundary. A numerical value may be recoverable if repeated elsewhere or uniquely computable from stated information. Structural errors require evidence that determines the intended direction or role. Clean references, hidden benchmark identities, memorized templates, and conventional domain assumptions are excluded as recovery evidence. Personas and semantic cues may help localize errors but cannot supply missing values. Likewise, model feasibility alone does not establish that a proposed correction is semantically valid. 

Annotation Implementation. Annotation uses gpt-5.6-sol with high reasoning effort through Codex, producing structured JSON records with preserved identifiers. The procedure consists of three passes with distinct evidence-access rules. • Blind annotation examines the ambiguous description and target metadata without access to clean references or historical model results. For each error, the annotator identifies observable evidence, considers alternative repairs, and assigns a recoverability label. • Reference auditing identifies the intended corruption and checks for overlooked evidence or unsupported assumptions. The clean reference remains excluded from information available to the repair model. • Adjudication resolves disagreements and flagged records under the same evidence bound-ary, separating metadata validity from recoverability. Labels are fixed before association with model outputs for performance evaluation.

Audit-trajectory-based harness optimization. The records contain two source-only prompt versions using the same uniqueness criterion. Development errors were examined through predicted actions, decisive evidence, unresolved issues, and explanations. Agent-assisted qualitative analysis produced five rules within the specified evidence boundary. First, the audit is restricted to modeling issues expressed in the description. Second, a complete, unqualified statement takes precedence over a tentative contradiction about the same element. Third, an alternative interpretation must specify a coherent competing OR element. Fourth, explicit local self-corrections can resolve uncertainty introduced earlier in the description. Fifth, necessary capacity, availability, and exact-requirement semantics apply without introducing new policies. The five rules were incorporated together in the final prompt version. Refinement used no separate distillation model, stored distillation prompt, or numerical rule-retention threshold. Rules are expressed in terms of evidence relationships and OR components, with sample identifiers, entities, and numerical answers removed. Related rules are consolidated under the uniqueness criterion, which requires Clarify when two materially different repairs remain supported. For example, an explicit capacity statement may resolve a later tentative reversal, whereas an uncertain numerical value remains unresolved without an exact replacement. Benchmark knowledge, conventional domain assumptions, and downstream solution outcomes are excluded from the admissible evidence. The repair agent uses gpt-5.5 with high reasoning effort and the frozen V3 protocol. Its output schema requires task_id , action , questions , fact_states , revised_description ,

Input mapping and evidence states. The recorded verifier_handoff contains the verifier action v and report w. Source-Sufficiency Verifier 

# Evidence-Bound Source-Sufficiency Verifier You are a binary reliability Verifier for operations-research problem descriptions. You receive only an original noisy user description. Your task is not to repair it and not to judge any alignment output. Decide whether the description itself contains enough observable evidence to uniquely repair every modeling-relevant error or ambiguity. The only actions are: - ‘ACCEPT‘: every modeling-relevant issue has exactly one correction supported by the description, its cross-sentence context, an explicit opposite relation, dimensional or structural consistency, or a necessary OR relation. - ‘CLARIFY‘: at least one issue admits multiple materially different corrections or depends on information absent from the description. ## Evidence-ledger procedure 1. Inspect the objective, decision variables, parameters, constraints, units, periods, and policy status. Record every modeling-relevant uncertainty, contradiction, omission signal, secondhand statement, and hard-versus-soft ambiguity. 2. For each issue, enumerate the materially distinct repairs compatible with the observed text. The source is sufficient only when one repair remains. 3. Treat an alleged issue that leaves the OR element already correct as requiring no repair. Do not invent ambiguity merely because prose is informal or omits textbook notation. 4. A remembered reversal can be resolved when the text explicitly supplies the intended opposite relation. Capacity or availability may establish an upper bound, explicit choice language may establish a decision variable, and "as high/low as possible" may establish an objective, but use such relations only when they uniquely settle the stated issue. 

60 5. An uncertain number without an exact replacement is unresolved. A possibly missing constraint, policy, unit, period, threshold, or enforcement status is unresolved when its content cannot be reconstructed from the text. 6. Limited-role language such as "another team handles it" or "I only track" does not justify deleting a possible requirement. Deletion is one possible repair, not evidence that deletion is correct. 7. Do not infer a hidden benchmark, copy a familiar textbook formulation, use conventional values absent from the text, or use downstream answer agreement. ## Decision boundary refinements - Evaluate the repairability of contradictions and uncertainty actually expressed in the description. Do not reject a description merely because it lacks formal notation or details that are neither disputed nor signaled as part of the model. - When the same OR element is stated both explicitly and tentatively, prefer the explicit, first-person, unqualified statement over a later hedge, recollection, or secondhand alternative. If this leaves one correction, the issue is resolvable. - A tentative alternative that cannot form a coherent model because it lacks a required threshold, conversion, or independent role does not by itself create a second viable repair when the description already states the complete coherent formulation. - Treat local self-correction as sufficient evidence: phrases such as "although I sometimes think", "someone told me", or "maybe" can be discarded when an earlier or later unequivocal statement supplies the exact value, unit, direction, role, or hard constraint. - For a claimed resource limit, physical availability, fixed capacity, or exact visit requirement, use the necessary upper-bound or hard-constraint semantics when explicitly stated. Do not invent a lower bound, soft target, or additional budget constraint that conflicts with that semantics. Set ‘source_sufficient=true‘ and ‘action=ACCEPT‘ exactly when all issues are uniquely resolvable. Otherwise set ‘source_sufficient=false‘ and ‘action=CLARIFY‘. You receive an original noisy description, an initial aligned draft, a frozen Verifier handoff, visible issue slots, and the dialogue history. You must acquire missing evidence from the user and directly repair the description. Never call or defer to another Alignment Agent. ## Evidence states Assign every visible ‘fact_id‘ exactly one state on every step: - ‘UNKNOWN‘: no relevant feedback has been obtained. - ‘SUPPORTED‘: user feedback completely and consistently establishes the required value, unit, period, role, direction, or hardness with adequate provenance. - ‘PARTIAL‘: relevant information is present but a required attribute remains missing. - ‘CONFLICTING‘: two material claims cannot simultaneously hold and precedence is unresolved. - ‘UNVERIFIED‘: a claim is reported but its entity, version, period, source, or authority is not established. - ‘UNAVAILABLE‘: the user has established that the required information cannot be obtained from the available environment. The source description, aligned draft, and Verifier handoff may identify or motivate an issue, but they are not post-clarification evidence. They must never promote an issue slot to ‘SUPPORTED‘. Before the first user response, every visible issue slot remains ‘UNKNOWN‘ and every interactive task must use ‘ASK‘. 

61 Do not classify the whole conversation into a scenario type. Judge each fact independently from user-supplied evidence. ## Action policy 1. For ‘NO_INTERACTION_CONTROL‘, return ‘NO_INTERACTION‘, ask nothing, and preserve the initial aligned draft. 2. Before feedback, ask concise, non-leading questions covering every visible unresolved ‘fact_id‘. Related facts may share one question, but list every covered ID. 3. After feedback, ground each claim to the corresponding fact and update all states. 4. Use ‘ASK‘ while any fact is ‘UNKNOWN‘, ‘PARTIAL‘, ‘CONFLICTING‘, or ‘UNVERIFIED‘ and another targeted question can make progress. 5. Use ‘ESCALATE‘ when a material fact is ‘UNAVAILABLE‘, the turn budget is exhausted, or unique repair remains impossible. 6. Use ‘FINALIZE‘ only when every visible fact is ‘SUPPORTED‘ by user feedback and the revised description incorporates every supported correction. Before ‘FINALIZE‘, perform a completeness audit over the union of the original noisy description, the initial aligned draft, and grounded feedback. The final description must be a self-contained OR problem, not a short patch summary. An omission in the initial aligned draft is not evidence that the omitted information is unnecessary. ## Direct repair - Revise the description yourself by minimal editing. - Treat the initial aligned draft as a fallible working draft, not as ground truth. - Change only elements supported by the original description or grounded user feedback. - Preserve correct, undisputed content and all needed problem data. - Restore all exact, uncontested data from the original noisy description when the initial aligned draft omitted them, including coefficient tables, entity-specific values, units, and structural requirements. - Every applied edit must cite a supporting user-feedback quote and its ‘fact_id‘. - Never invent an exact number, unit, period, objective, constraint direction, variable role, or policy from typical OR practice. - Do not accept an outdated or memory-only record when its authority or version is unresolved. At finalization, verify that the output still states all material entities and choices, the complete objective, every required constraint, and every coefficient needed to instantiate or solve the model. If these are available in the original description, include them without asking the user again. Return one schema-compliant prediction for every input ‘task_id‘. Use only fact IDs appearing in that task’s ‘issue_slots‘.

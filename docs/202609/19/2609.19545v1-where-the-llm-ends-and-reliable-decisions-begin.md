## 摘要
将优化问题的自然语言描述转化为求解器可用代码的系统，通常在每个阶段都使用语言模型，包括从数学形式化到可执行建模代码的最终转换。我们提出 ANVIL 编译器架构，将这些问题分离。语言模型只调用一次，在基于问题类型的约束引导辅助下，生成 LaTeX 形式化。随后，确定性编译器将该 LaTeX 转换为代码，全程不涉及语言模型。我们描述了该确定性编译器（归一化器、生成类型化中间表示的递归下降解析器、将符号绑定到数据集模式的分析遍，以及代码生成器），并在 NLP4LP 基准的 354 个简单和困难问题上评估了它。编译器为 354 个形式化中的 329 个生成了代码（92.9%），在所有这些情况下都走确定性路径，从未回退到模型生成的代码。中位编译时间低于我们计时器的 10ms 分辨率。总体而言，我们的形式化在简单问题上达到 98.9% 的准确率，在困难问题上达到 91.1%。编译数据与准确率数据之间的差距是一个关键分析点，我们对其进行了分析：未能编译的形式化、返回不可行的问题、运行时引发错误的问题，以及返回错误目标值的问题。几乎所有这些错误都可追溯到形式化本身，而不是转换过程。ANVIL 在领先基准上表现异常出色，因为它将语言模型纯粹用于其有效之处，而不是作为万能工具。

## Abstract
Systems that turn natural-language descriptions of optimization problems into solver-ready code generally use a language model at every stage, including the final translation from a mathematical formulation into executable model-building code. We propose the ANVIL compiler architecture, where we separate these concerns. A language model is called only once, assisted by constraint guidance based on problem type, to produce a LaTeX formulation. A deterministic compiler then translates that LaTeX into code with no language model involvement. We describe the deterministic compiler (a normalizer, a recursive-descent parser producing a typed intermediate representation, analysis passes that bind symbols to a dataset schema, and a code emitter) and evaluate it on the 354 easy and hard problems of the NLP4LP benchmark. The compiler produced code for 329 of 354 formulations (92.9%), taking the deterministic path in every one of those cases and never falling back to model-generated code. Median compile time was below the 10ms resolution of our timer. Overall, our formulations achieved an accuracy of 98.9% over easy problems and 91.1% for hard problems. The gap between these compilation and accuracy figures is a key point of analysis, and we analyze it: formulations that failed to compile, problems that returned as infeasible, problems raising errors at runtime, and problems returning a wrong objective. Almost all of these errors trace back to the formulation rather than to the translation. ANVIL performs exceptionally well on leading benchmarks by using language models purely where they are effective, rather than as a catch-all tool.

# 《Where the LLM Ends and Reliable Decisions Begin》论文总结

## 1. 核心问题与整体含义

- **研究动机**：现有“自然语言优化问题 → 求解器代码”的系统通常让 LLM 贯穿全流程，包括参数抽取、约束形式化、代码生成与调试。这样做的代价是：最终代码翻译阶段也继承了生成模型的随机性，导致同一输入可能产生结构不同的代码，变量名、求和范围、索引等都可能变化，且错误难以检测和归因。
- **核心问题**：是否必须在所有阶段都使用 LLM？尤其是从数学形式化到可执行建模代码的“翻译”阶段，是否可以用确定性编译器替代 LLM？
- **整体含义**：论文提出 ANVIL 架构，将“建模/形式化”与“翻译/代码生成”解耦。LLM 只调用一次，用于生成 LaTeX 形式化；之后由确定性编译器完成到 PuLP 代码的翻译。其核心主张是：LLM 应只用于其擅长的环节，而可靠决策所需的翻译阶段更适合确定性系统。

## 2. 方法论：ANVIL 架构与关键技术

- **核心思想**：  
  `自然语言问题 + 问题类型 + 约束引导 + 数据 schema 摘要 → LLM 一次调用 → LaTeX 形式化 → 确定性编译器 → PuLP 代码`。  
  翻译阶段完全不使用语言模型。
- **编译器四阶段**：
  - **Normalizer 归一化器**：将 LaTeX 重写为规范形式，处理求和下标、空格、乘法符号、集合隶属写法等不一致；修复如双重下标 `\sum_{i=1}` 被模型误写成索引集/范围混淆的问题。
  - **Parser 解析器**：对归一化 LaTeX 做递归下降解析，生成类型化中间表示 IR。支持索引求和、嵌套求和、系数分配、big-M、SOS1/SOS2、变量域声明等。关键难点是区分“变量域声明”和“索引集声明”，以及处理字面下标。
  - **Analyzer 分析器**：共 12 个固定顺序的分析 pass，将语法有效的形式化绑定到具体数据集，并拒绝无法验证的模型。典型 pass 包括：解析集合名、构造派生集合、双向验证、完整性验证、线性验证等。
  - **Emitter 代码生成器**：读取已验证 IR，生成 PuLP 代码。输出是确定性的：集合按解析顺序迭代，名称来自 IR 字段，不依赖字典迭代顺序或哈希，因此同一 IR 在不同运行和机器上产生字节级相同代码。
- **IR 中间表示**：
  - 描述带索引集合的 MILP。
  - 枚举变量类型：连续、整数、二值；目标方向：最小化、最大化；约束方向。
  - 支持集合声明、派生集合、函数映射、参数声明、宽表格式、连接表、标量/派生/基数/字面量参数、变量声明及稀疏定义域等。
- **符号解析策略**：
  - 先尝试精确匹配；失败后按索引变量匹配；再失败则用序列相似度，阈值 0.75，并做去复数化处理。
  - 当两个符号竞争同一字段时，使用打分 tiebreaker，失败者重新解析。
  - 通过双向单射验证防止模糊匹配把两个不同参数绑定到同一列，否则会产生“可运行但答案错误”的模型。
- **拒绝机制**：
  - 完整性 pass 拒绝引用未声明符号的形式化。
  - 线性 pass 拒绝决策变量乘积，因为目标求解器为 MILP。
- **修复循环**：
  - 编译失败时先做有界的逐约束修复，累计错误历史，避免重复无效修复。
  - 三次失败后才可选调用 LLM 生成受影响部分代码。但本文评估完全禁用该回退，所有报告编译均走确定性路径。

## 3. 实验设计

- **数据集/benchmark**：NLP4LP，共 361 题，来自优化教材和讲义。论文使用其中 354 个 easy 和 hard 问题，排除 7 个 case study。
  - Easy：289 题；Hard：65 题。
  - 354 题中，320 题有可用于自动评分的数值目标值；34 题无；其中 22 题参考状态为 infeasible/unbounded，按状态一致性评分；12 题无可用参考答案，排除在所有准确率之外。
- **评分规则**：
  - 有数值参考时，比较目标值：若参考为 0，则绝对误差 `< 1e-6`；否则相对误差 `≤ 0.001`。
  - 参考为 infeasible/unbounded 时，比较求解器状态是否一致。
  - 准确率定义为 `match / (match + mismatch)`，即条件于系统已产生可评估答案，因此不反映覆盖率。
- **形式化生成**：
  - 每个问题由语言模型生成 5 次形式化并缓存。
  - 报告结果使用“编译率最低”的那一组样本，以固定输入、避免采样乐观偏差，偏保守评估。
- **求解设置**：
  - 使用 PuLP 自带的 CBC 求解器，在子进程中运行。
  - Easy 和 hard 分开运行，总 wall clock 约 78 秒。
- **对比方法**：
  - 论文没有直接头对头复现所有 baseline。
  - 与 OptiMUS 的数字做了非直接比较：OptiMUS 报告最佳约 80.3%（o1）和 73.7%（GPT-4o）；本文最接近的指标是“全部 320 个有数值参考问题上的 93.4% 匹配率”，而非条件准确率 97.7%。
  - 定性讨论了 SolverLLM、AlphaOPT、LM4OPT、LLaMoCo、SMILO、NL4Opt、Mamo、OptiChat 等工作，说明本文在“把 LLM 移出代码翻译环”这一点上的差异。
